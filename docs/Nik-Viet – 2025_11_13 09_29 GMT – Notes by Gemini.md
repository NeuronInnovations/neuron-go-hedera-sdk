### Summary

Nikolaos Siafakas and Do Hoang Viet discussed issues with the Go SDK, noting that the AI agent's documentation needs improvement, and that the SDK is flawed because the underlying libp2p documentation is poor and its features are not fully used due to the team's decision to forgo the DHT, which relies on Hedera for discovery instead. Key problems identified include unreliable hole-punching, the lack of bandwidth management resulting in system degradation from slow connections, and significant inefficiencies from using only one persistent stream per peer, which should be changed to allow users control over opening and closing cheaper streams. A major underlying issue is the lack of state management, which causes repeated expensive account creation and connection loss, leading to the decision to implement a small, embedded database, like Bolt DB, to remember IP addresses and message topics, with Do Hoang Viet to decide on the optimal writing frequency.

### Details

* **Review of Documentation and Tools** Nikolaos Siafakas and Do Hoang Viet discussed the documentation generated by an AI agent on the Go SDK repository. Nikolaos Siafakas noted that the AI agent is creating diagrams using Mermaid or Ascii formats, which Do Hoang Viet believes can be made more comprehensive for newcomers ([00:00:00](?tab=t.wke86ud5t55a#heading=h.cvy2ktq74mw)). Nikolaos Siafakas expressed concern that the AI cannot identify the SDK's flaws because the underlying libp2p documentation is poor ([00:01:22](?tab=t.wke86ud5t55a#heading=h.ti1r3eolfc1i)).

* **Libp2p System and Flaws** Nikolaos Siafakas provided background on the peer-to-peer system, where a buyer and a seller establish a connection after listening to a topic ([00:05:21](?tab=t.wke86ud5t55a#heading=h.84t6fjpa3grf)). They explained that a significant flaw is that the dial from the seller to the buyer can fail if the buyer has not port forwarded or enabled UPNP. Libp2p's specialties include creating multiple multiplexed streams over the same port, using UDP for better NAT traversal, built-in encryption, and hole-punching capabilities to bypass firewalls ([00:06:24](?tab=t.wke86ud5t55a#heading=h.4iys3pq95o6)).

* **Relay and Proxy Functionality** Nikolaos Siafakas highlighted that libp2p allows peers to hole punch through firewalls and, if that fails, use a relay or proxy ([00:09:20](?tab=t.wke86ud5t55a#heading=h.g8myywtt7yrj)). They noted that a relay is also beneficial when a peer has low upload bandwidth, allowing them to send data to a relay with better internet for distribution ([00:11:16](?tab=t.wke86ud5t55a#heading=h.2jeovd52llaq)). The system is designed to allow addressing a sensor's EVM address via a proxy, but they are not currently using these specialized addresses because the relay is not in use ([00:25:10](?tab=t.wke86ud5t55a#heading=h.v3i9goe3ztc9)).

* **Drawbacks of DHT and Consequences of Non-Use** The speakers identified significant problems with using the Distributed Hash Table (DHT) in libp2p: it advertises a user's IP and EVM address, which Do Hoang Viet called "terrible". Additionally, using DHT requires running a DHT server, which Nikolaos Siafakas deemed too expensive and complex for their use case, preferring to leverage Hedera for discovery instead ([00:14:19](?tab=t.wke86ud5t55a#heading=h.32pyj9pclyvb)). The decision to forgo DHT in favor of Hedera, which was Nikolaos Siafakas's idea, results in a loss of certain libp2p benefits, particularly the ability to use the relay for hole punching, as the libp2p relay relies on DHT ([00:17:01](?tab=t.wke86ud5t55a#heading=h.o88z1hlybqc0)).

* **Hole Punching and Relay Challenges** Because the team does not use the DHT, they cannot use libp2p's hole punching ability, which is reliant on the libp2p relay. Nikolaos Siafakas stated that their custom-written hole-punching solution "doesn't work well" ([00:20:06](?tab=t.wke86ud5t55a#heading=h.tvq0ae7476jb)). They posed two solutions: either investigate the libp2p relay to imitate its function with Hedera, or re-examine libp2p's documentation, as Nikolaos Siafakas might have misunderstood that DHT is integral to the relay functionality ([00:21:12](?tab=t.wke86ud5t55a#heading=h.17q3fcn5rkr6)). A key requirement is to make hole-punching reliable and to implement proxies/relays for better bandwidth management ([00:22:17](?tab=t.wke86ud5t55a#heading=h.6dcedt8mbb3l)).

* **SDK Deficiencies: Bandwidth Management and Slow Connections** Nikolaos Siafakas pointed out that the current SDK lacks a system to limit direct connections or enforce the use of proxies, leading to potential overload if many people request data from a low-bandwidth seller ([00:27:12](?tab=t.wke86ud5t55a#heading=h.3nrzkg6zdcrm)). The current system uses a "cowboy random" method for serving requests (first-come, first-served), which is not ideal ([00:31:13](?tab=t.wke86ud5t55a#heading=h.2of1k4klu7lx)). A significant coding deficiency is that slow connections degrade the performance of the entire system because the data copying process is not well multi-threaded; good coding would isolate the slow connection into its own thread ([00:32:30](?tab=t.wke86ud5t55a#heading=h.9xabnajzogw1)).

* **Language and Implementation Details** The SDK is written in Golang, which Nikolaos Siafakas noted is very fast, an essential requirement for aviation data services. They acknowledged that Rust would be the best choice for its multi-threaded capabilities, but Golang is a good compromise due to the difficulty of finding enough Rust developers ([00:35:12](?tab=t.wke86ud5t55a#heading=h.ptknoxvheho1)). They also observed that libp2p's features are not fully developed across all supported languages, with Go having the most complete version ([00:37:25](?tab=t.wke86ud5t55a#heading=h.cb88lb11hz0a)). Nikolaos Siafakas also noted that libp2p documentation is lacking, and the community forums are inactive, making it difficult to get support ([00:38:39](?tab=t.wke86ud5t55a#heading=h.88cf609s6pv6)).

* **Inefficient Stream Management** A technical issue with the current SDK is that it only uses one stream per peer-to-peer connection and tries to keep that stream open indefinitely. Nikolaos Siafakas explained that this approach is inefficient because opening and closing streams once a connection is established is very cheap, which they were unaware of due to lack of documentation ([00:42:01](?tab=t.wke86ud5t55a#heading=h.rv6c3dinyax9)). The SDK should give users control over opening and closing streams, especially for services with infrequent requests, as the current system triggers a complete tear-down and restart of the connection via Hedera whenever a stream breaks ([00:45:15](?tab=t.wke86ud5t55a#heading=h.nh2tn6i3pan2)).

* **Absence of State Management** The major underlying issue causing connection loss and service restarts is the lack of state management, meaning the system does not remember IP addresses or shared money accounts ([00:46:50](?tab=t.wke86ud5t55a#heading=h.urevdnfpj86h)). Task number one is to implement a way to remember IP addresses, which Do Hoang Viet suggested using Redis for. Nikolaos Siafakas cautioned that the solution must be incredibly small, perhaps like an embedded database such as Bolt DB, as Redis might be too large for the devices they use ([00:49:16](?tab=t.wke86ud5t55a#heading=h.wn9lgrdu0b63)).

* **Shared Account Creation Costs** Nikolaos Siafakas noted that the lack of state causes the buyer to create a new, expensive shared money account with the seller every time they talk after a reboot, instead of remembering and reusing the existing account ([00:56:28](?tab=t.wke86ud5t55a#heading=h.frt0ziymtwos)). They emphasized that this penalty is paid because the system is currently stateless, but they must find a way to maintain necessary state without relying on a traditional hard disk that could burn out, such as an SD card ([00:57:36](?tab=t.wke86ud5t55a#heading=h.1sogpcq3szj)). Previous attempts to create a custom file-based database resulted in corrupted files and failed device launches ([00:52:28](?tab=t.wke86ud5t55a#heading=h.5tul8d34xxvf)).

* **Database for IP Addresses and Message Recall** Nikolaos Siafakas and Do Hoang Viet discussed methods for finding a user's IP address without going to the main database, suggesting utilizing the input topic to find who requested what and when. Although Do Hoang Viet noted this approach is resource-consuming, Nikolaos Siafakas accepted this could be a solution, while highlighting the potential issue of the blockchain being down, which prevents access ([00:58:45](?tab=t.wke86ud5t55a#heading=h.l42s9fxxfghb)). Nikolaos Siafakas emphasized the need to remember messages from a Hedera topic, perhaps for one day's worth of messages, and creating a small database that remembers these topics, advising to write only when necessary to avoid excessive writing ([00:59:53](?tab=t.wke86ud5t55a#heading=h.o4pzfp8m15hv)).

* **Optimizing Database Writing Frequency** Do Hoang Viet suggested setting an interval, such as every 10 minutes or seconds, for devices to write lists of IP addresses to the database. Nikolaos Siafakas proposed a reactive approach using the libp2p event bus, which signals when something, like an IP address, has changed, or to only write when a new service request is received from the blockchain. Ultimately, Nikolaos Siafakas deferred the final decision on the best method for avoiding excessive writing to Do Hoang Viet's intuition ([01:01:01](?tab=t.wke86ud5t55a#heading=h.x3z916ef14jd)).

* **Sharing Meeting Artifacts** Do Hoang Viet requested to export the diagram Nikolaos Siafakas wrote during the meeting to use as context for AI later ([00:59:53](?tab=t.wke86ud5t55a#heading=h.o4pzfp8m15hv)).
